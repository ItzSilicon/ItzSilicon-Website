OAuth 2.0 現代網頁授權深度解析

Evolution

技術歷史沿革

從「密碼共享」到「無密碼授權」，OAuth 經歷了從 2006 年的概念發想到 2012 年 Token 化框架的完整演進。

  1. 2006

    密碼共享的困境

    第三方 App 若要存取 Gmail、Google 地圖等資源，必須取得使用者密碼，造成密碼洩漏風險與權限失控。

  2. 2007

    OAuth Core 1.0 草案

    Blaine Cook、Larry Doolittle 等人組成開放社群，於 10 月 3 日發布 OAuth Core 1.0 最終草稿[3]。

  3. 2010

    RFC 5849

    OAuth 1.0 進入 IETF 標準化，成為業界共通的授權協議[3]。

  4. 2012

    OAuth 2.0 (RFC 6749 / RFC 6750)

    發布更靈活、可擴展的 Token 授權框架，並明確定義 Bearer Token 使用規範。

  5. 2013+

    威脅模型與 OAuth 2.1

    IETF 發布威脅模型，王景提出 Covert Redirect 變體；OAuth 2.1 簡化並淘汰 implicit 等不安全流程。

Foundation

API 與 OpenAPI 基礎

理解 OAuth 之前，必須先掌握 API 與 OpenAPI：前者是應用程式之間的介面，後者讓 API 變得機器可讀。

API

API 的抽象化價值

API（Application Programming Interface）是軟體元件、應用程式或服務之間溝通的規則與工具集合[9]。它抽象化了底層實作，讓開發者能透過簡潔介面使用強大功能，例如在金融場景中常見的開放銀行 (Open Banking) 資料交換[13]。

  • 瀏覽器內建 API：DOM、Fetch、Canvas、IndexedDB。
  • 第三方 API：Google Maps、Facebook、PayPal 等。
  • 資料存取 API：LocalStorage、IndexedDB 離線儲存。

OpenAPI

OpenAPI Specification (OAS)

OpenAPI 是一種機器可讀的 API 描述規格[4]，使用 YAML 或 JSON 標準化定義端點、HTTP 方法、參數、請求與回應格式、安全機制等細節[5][7]。

  • 標準化：語言無關，適用任何技術堆疊。
  • 自動化：Swagger UI、OpenAPI Generator 自動生成文件與 SDK。
  • 維護：由 OpenAPI Initiative 管理，最新版本 3.1.0。

Core Roles

OAuth 核心角色

OAuth 2.0 定義了四個互動角色，授權流程即是這四者在授權伺服器中協作的結果[15]。

01

Resource Owner

資源擁有者

通常是使用者本人，擁有資料並決定是否授權第三方應用程式存取。

02

Client

客戶端應用程式

想要存取使用者資料的第三方服務，例如支援「用 Google 登入」的網站或 App。

03

Authorization Server

授權伺服器

負責驗證使用者、取得同意，並核發 Authorization Code 或 Access Token。

04

Resource Server

資源伺服器

保存受保護資料的 API 伺服器，會檢查 Access Token 有效性後才回傳資料。

Authorization Flow

授權運作流程

流程重點是「密碼不交給第三方」，Client 取得的是可限制範圍與期限的 Token[1][2]。

Token 取代密碼

第三方應用不需要知道使用者密碼。

Scope 限制權限

只允許存取必要資料，例如 email 或 profile。

Token 有效期限

權杖可設定短效期以降低外洩風險。

授權可撤銷

使用者可在帳號設定移除第三方授權。

授權請求範例

GET /authorize?
  response_type=code&
  client_id=CLIENT_ID&
  redirect_uri=https://client.example/callback&
  scope=profile email&
  state=RANDOM_CSRF_TOKEN&
  code_challenge=PKCE_CHALLENGE

API 呼叫範例

GET /v1/me
Authorization: Bearer ACCESS_TOKEN

回應資料只應包含授權 Scope 允許的欄位

OpenAPI x OAuth

實務宣告：OpenAPI x OAuth 2.0

OpenAPI 透過 securitySchemes 定義授權機制[4][6]，打通前後端溝通[8]，並在操作層級透過 security 宣告使用哪些 Scopes[10][11]。

openapi-spec.yaml 
components:
  securitySchemes:
    OAuth2Flow:
      type: oauth2
      flows:
        authorizationCode:
          authorizationUrl: https://auth.example.com/oauth/authorize
          tokenUrl: https://auth.example.com/oauth/token
          scopes:
            read:profile: "讀取使用者公開資料"

security:
  - OAuth2Flow:
      - read:profile

此宣告讓 Swagger UI、OpenAPI Generator 等工具自動產生可互動的授權按鈕、SDK 與安全測試流程。

Security Analysis

安全性分析

OAuth 框架本身設計嚴謹，但實作錯誤或使用者無意識授權，仍可能導致嚴重風險。

資安威脅情報 (Threat Intelligence)

當前 OAuth 攻擊已能繞過多因素驗證 (MFA)

根據資安實務統計，近年駭客開始大量利用偽造的 OAuth 應用程式來繞過多因素驗證 (MFA)，其 攻擊成功率已超過 50%。 這使得針對重定向網址劫持的防範與 PKCE 的部署成為現代 Web 安全的重中之重。

常見攻擊與風險

偽造 OAuth 應用程式 (關鍵威脅)

駭客偽裝成 Adobe、DocuSign 等合法服務誘騙使用者授權，研究顯示此攻擊繞過 MFA 成功率超過 50%[14]，2025 年已影響逾 900 個 Microsoft 365 環境。

CSRF 攻擊

若未正確使用 state 參數，攻擊者可偽造授權請求，讓使用者無意中授權惡意應用。

Token 洩漏

Access Token 若放在 localStorage、未加密日誌或被 XSS 讀取，可能導致資料外洩。

授權碼攔截

公開客戶端若未使用 PKCE，攻擊者可能攔截 Authorization Code 並換取 Token。

威脅模型 (Threat Model)

IETF 系統性定義 OAuth 風險，開發者需依此模型評估應用安全。

防護最佳實務

強制使用 PKCE

SPA、行動 App 等公開客戶端應使用 PKCE 防止授權碼被攔截[16][15]。

驗證 state 參數

state 必須隨機、唯一且與使用者 Session 綁定，用於防範 CSRF。

安全儲存權杖

Web 使用 HTTP-only、Secure Cookie；行動端使用 Keychain 或 Keystore。

最小權限原則

只要求必要 Scope，並定期檢查、撤銷不再需要的第三方授權。

使用者警覺

點擊「允許」前確認應用名稱與請求權限，警惕釣魚郵件。
